Customer Q&A
AI 하나로 테스트를 전부 자동 생성할 수는 없나요?
순수 AI 단독 생성은 약 57점(F) 수준에 머뭅니다. 화면 대분류는 잘 맞히지만, 사전조건·시험절차·예상결과 같은 업무 맥락 항목의 정확도가 낮습니다.
해법은 사람의 작업 규칙을 정리해 AI에게 학습시키고, 생성 → 사람 검토 → 규칙 개선을 반복하는 것입니다. 이 노선으로 품질이 70 → 84점까지 수렴했습니다.
AI 단독 57.4점 (F) 규칙 기반 84점 (합격선 60) F1 기준 약 2배 향상
한 시스템에 맞춘 규칙이, 다른 기획서에도 통하나요?
이번 분기에 처음으로 입증했습니다. 공문발송 시스템용으로 다듬은 동일한 도구를, 코드 수정 없이 전자고지서 기획서에 적용해 메뉴트리를 자동 생성했습니다(5개 화면 전수, 0 → 22행).
기획서마다 다른 작성 습관(라벨 이름, 자리표시자 등)은 규칙의 "별칭/차단" 확장으로 흡수했고, 기존 시스템에는 영향(회귀) 0건이었습니다.
적용 기획서 2번째 (전자고지서) 인식 화면 0 → 5 기존 영향 회귀 0건
검토 의견(피드백)은 어떻게 반영되나요?
검토 의견을 받으면 6단계 협업 사이클(의견 추출 → 원인 분석 → 규칙 보완 → 재생성 → 채점 → 채택)이 돌고, 사람이 두 곳에서 승인합니다. 지난 두 달간 4개 사이클로 누적 35건(공문발송 4 · 11 · 12 · 8건)을 처리했고, 가장 최근의 대표 사이클에서는 12건 중 84.6%를 해소했습니다.
2달 누적 35건 · 4개 사이클 대표 사이클 12건 · 84.6% 해소 처리 방식 자동 + 사람 승인 2곳
내부 규칙 자산 — TBT/TC 완성도 엔진 P0 핵심 규칙 정의 현황
규칙은 코드가 아니라 자산입니다. 사람의 작업 원칙을 규칙 한 줄로 정의하면 모든 버전·모든 기획서에 적용되고, 각 규칙은 "재발 방지 검사"와 짝을 이뤄 한 번 올린 완성도가 다시 무너지지 않게 지킵니다. 현재 생성 규칙 약 80개(R0·T 계열) + 재발 방지 검사 60여 개가 누적된 상태입니다.

회귀 감지 시 직전 정상본으로 즉시 롤백 (실제 4회 작동)
안전성이 가장 큰 성과입니다. 자동 사이클(하네스 엔지니어링)을 도입한 두 달간, 어떤 변경도 문서를 완전히 망가뜨린 채 채택된 적이 한 번도 없습니다. 위험한 변경은 채택 전 자동 점검·채점에서 걸러지고, 회귀가 감지되면 즉시 직전 정상본(baseline)으로 롤백했습니다(실제 4회 작동). 덕분에 큰 개선도 "시도 → 문제 시 되돌리기"로 두려움 없이 전진할 수 있었습니다.
비결은 규칙을 고칠 때 "재발 방지 검사 룰"을 짝으로 함께 만들어 두는 것 — 한 번 잡은 결함이 다시 들어오면 자동 감지되고, 자동 검사가 잔존 문제를 짚어 다음 개선을 스스로 점화합니다.
품질을 어떻게 측정하는가 평가 기준
산식: 5개 카테고리 · 25+개 메트릭에 가중치를 적용한 가중평균 × 100. 메트릭마다 "규칙을 지킨 행 ÷ 검사 대상 행"을 점수화하고, 카테고리 가중치(아래 막대 우측)로 합산합니다. 합격선 60점 미달 시 다음 단계(TC) 진행 불가 — 매 생성마다 자동 실행되어 사람 검토 없이도 품질 하락을 즉시 포착합니다.

측정은 3겹으로 — 자동에서 사람까지
Layer 1 · 자동 채점
매 생성 시 25+ 메트릭
생성 직후 모든 규칙 준수 여부를 자동 계산. 합격선 60점 미달 시 다음 단계 진행 차단.
Layer 2 · 구조 게이트
정답 없이 구조 완전성
검증 행 패턴 · 사전조건 커버리지 · 흐름 미연결 · 행 수 안정성 · 멱등성(2회 실행 100% 동일)을 측정.
Layer 3 · 사람 검증
검토 요청 + 피드백 사이클
외부 검토자에게 검토 요청서 등록 → 받은 피드백을 6단계 협업 사이클로 반영.
이 채점의 강점은 Reference(정답) 없이 규칙 준수도만으로 측정한다는 점 — 정답본이 없는 새 기획서도 즉시 평가할 수 있습니다. 매 생성마다 자동 실행되어 사람 검토 전에 품질 하락을 포착하고, 카테고리별 점수가 약한 축(데이터 품질·경계값)을 드러내 다음 보강 대상을 가리킵니다. 자동 채점이 놓칠 수 있는 *의미적 정확성*은 아래 3겹 측정의 Layer 3(사람 검토)가 메워, 측정 신뢰도를 확보합니다.
스크립트화 준비 — 실행 가능한 테스트로 다음 단계 (6월~) 파이프라인 설계
파이프라인의 다음 단계는 TC → 자동화 스크립트(Playwright) 변환입니다. 스크립트는 사람과 달리 암묵적 맥락을 읽지 못하므로, ① 어디로 이동하고 ② 무엇을 순서대로 ③ 어떤 요소를 ④ 어떻게 검증할지가 모두 명시되어야 실행됩니다. 그래서 이번 분기 TBT/TC 룰을 "완성도"뿐 아니라 "기계 실행 가능성" 기준으로도 다듬어 다음 단계의 포석을 미리 깔았습니다.

바탕에는 동작 유형 코드(클릭 · 사전조건 · 입력 · 결과 표출 · 검증 · 호버)가 있어, 각 코드가 스크립트 동작으로 1:1 변환되는 어휘 역할을 합니다. 6월부터 시작하는 스크립트 생성 단계(S 시리즈 룰)는 위 포석 위에서 출발합니다.
